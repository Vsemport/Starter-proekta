# Как мы пишем код

> Подключается к `CLAUDE.md`, читается в каждой сессии. Правила по умолчанию для любого стека; дополни своими. Правила для отдельных папок — в `.claude/rules/`.

## Изменения
- Одно изменение — одна причина. Не смешивай переименование, рефакторинг и новую функцию в одном коммите.
- Маленькие шаги: изменение, которое нельзя объяснить одним предложением, делится на несколько.
- Не трогай код вне задачи. Увидел проблему рядом — запиши в план или бэклог, не чини молча.
- Данные, которые меняются (цены, лимиты, даты, адреса, ключи) — в конфигурации или базе, не в коде.

## Качество
- Для нового поведения сначала тест, который падает, потом код. Если автоматический тест невозможен — заранее записанный проверяемый сценарий.
- Ошибки не глотаем: либо обрабатываем осмысленно, либо даём упасть с понятным сообщением.
- В логи и сообщения об ошибках не попадают пароли, токены и персональные данные.
- Перед закрытием фазы — `bash scripts/check.sh` без ошибок.

## Имена и структура
- Имена говорят, что это и зачем: `userEmail`, а не `ue`; `calculateInvoiceTotal`, а не `calc`.
- Файл отвечает за одну вещь. Файл длиннее ~300 строк — повод разделить.
- Тесты лежат рядом с кодом или в `tests/` — так, как принято в стеке (см. `docs/stack.md`), и не иначе.
- Комментарии объясняют «почему», а не «что». Устаревший комментарий хуже отсутствующего.

## Зависимости
- Новая зависимость — решение, а не привычка: зачем, кто поддерживает, лицензия, размер. Для спорных случаев — запись в `docs/decisions/`.
- Версии фиксируем (lock-файл в репозитории). Обновляем осознанно, с запуском проверок.

## Git
- Ветка на план: `plan/ГГГГ-ММ-ДД-название`. В `main` — только через PR с пройденными проверками.
- Сообщение коммита: что и зачем, в настоящем времени: «добавляет проверку лимита в корзине», не «фикс».
- Коммитим поимённо нужные файлы, не `git add .` (параллельные сессии могут менять соседние файлы).
- Секреты, `.env`, личные данные — никогда. Проверка перед коммитом: `.github/hooks/pre-commit.sample`.
